# Deviations from SRS / SAD / STP

Add a row whenever the implementation differs from a submitted document.

| Date | Document & section | What changed | Why |
|---|---|---|---|
| 2026-10-27 | SRS §4.2 (BBMS-F-010), SAD data model (`donations`, `blood_units`) | Added `donations.donation_type` (`WHOLE_BLOOD` / `APHERESIS`). An apheresis session creates one `PLATELETS` unit with a 5-day shelf life; whole blood creates a `WHOLE_BLOOD` unit with 35 days. *Pending team confirmation.* | F-010 requires recording the donation type, but the schema had no column for it, and `blood_units.component` has no apheresis value. Single-donor platelets are the most common apheresis product. |
| 2026-10-27 | SRS §4.2 (BBMS-F-011), SAD data model (`donations`) | Added `donations.post_hemoglobin_g_dl` (`DECIMAL(4,1)`). *Pending team confirmation.* | F-011 requires post-donation haemoglobin, but the schema only had post-donation BP and pulse columns. |
| 2026-10-27 | SRS §4.2 (BBMS-F-011) | Safe ranges used to flag vitals (inclusive): systolic BP 100–140 mmHg, diastolic BP 60–90 mmHg, pulse 60–100 bpm, haemoglobin 12.5–18.0 g/dL. Readings outside the safe range are **stored and flagged** (200 with `warnings`), not rejected. Readings that are impossible are rejected with 400: ≤ 0, systolic > 300, diastolic > 200, pulse > 250, haemoglobin > 25.0, BP/pulse not whole numbers, haemoglobin with more than 1 decimal, or diastolic ≥ systolic. *Pending team confirmation.* | The issue does not give the ranges. These are team assumptions and have **not** been checked against a cited clinical standard; only the 12.5 g/dL minimum comes from our existing F-002 eligibility rule. The 400 caps also keep values inside the `SMALLINT` / `DECIMAL(4,1)` columns. |
| 2026-10-27 | SRS §4.2 (BBMS-F-011) | Post-donation haemoglobin is **not** flagged when below 12.5 g/dL (it is still flagged above 18.0). All other post-donation ranges are the same as pre-donation. *Pending team confirmation.* | A drop in haemoglobin straight after donating is expected, so flagging it would warn on almost every donor. |
| 2026-10-27 | SAD API design (BBMS-F-011) | Vitals are recorded with `PUT /api/donations/:id/vitals/pre` and `PUT /api/donations/:id/vitals/post` (LAB_TECH only, same as F-010). All four readings are required per phase; sending a phase again overwrites it. Temperature is not part of F-011 and is not captured. *Pending team confirmation.* | Pre- and post-donation readings are taken at different times, so each phase is saved on its own. Overwriting lets staff correct typing mistakes. |
| 2026-10-27 | STP §6, §10 (BBMS-F-012) | No physical label printer or barcode scanner. Labels are printed with the browser's print dialog (`Print Label`); print CSS hides the rest of the page and prints the label 100 mm wide at the top-left of the page, with its height following the content (about 56 mm). No `@page` size is set, so any paper size and orientation works. Scanning is simulated by typing the unit ID into the lookup box and pressing Enter; a USB keyboard-style scanner would do the same, but this has **not** been tried with real hardware. *Pending team confirmation.* | Required by the issue: the STP makes the printer optional. The label size is an assumption, not taken from a standard. A label-sized `@page` can be added once the team picks real label stock. |
| 2026-10-27 | SRS §4.2 (BBMS-F-012) | The barcode is **Code 128** and encodes exactly the unit ID (`blood_units.unit_code`, e.g. `U-2026-000007`). Besides the required unit ID, blood group (`PENDING` until lab testing) and collection date, the label also shows the component and expiry date. *Pending team confirmation.* | Assumption: Code 128 can encode the letters, digits and dashes in our unit IDs and is read by ordinary handheld scanners. We have **not** checked the label against any blood-bank labelling standard. Expiry and component are already on the unit and are needed to handle a bag. |
| 2026-10-27 | SAD API design (BBMS-F-012) | Units are looked up with `GET /api/donations/units/:unitId` (collection module), allowed for LAB_TECH, MANAGER and ADMIN; HOSPITAL and DONOR get 403. The code is trimmed and upper-cased first. A code that isn't shaped like a unit ID gets 400, a well-formed one that doesn't exist gets 404. The `POST /api/donations` response is unchanged. *Pending team confirmation.* | The SAD has no endpoint for unit lookup. Lab techs print labels; managers and admins may need to identify a bag. Hospitals and donors have no reason to look up bags by barcode. |
| 2026-11-02 | SRS §4.1 (BBMS-F-001, F-003), §4.2 (BBMS-F-010, F-011, F-012), SAD client architecture | Unified Blood Collection Desk Wizard replacing disconnected standalone forms. The UI guides staff through (1) Donor Check-in (new donor registration or searching existing donors by Donor ID/Phone), (2) Donation Session initialization and vitals capture in one atomic step (calling `POST /api/donations` and `PUT /api/donations/:id/vitals/pre`), and (3) immediate barcode unit label generation with post-draw recovery observation. Standalone tabs for Vitals and Labels remain available for direct lookup/reprints. | The SRS/SAD specified individual endpoints and features in isolation, which led to a disconnected UI: newly registered donors (`D-XXXXXX`) had no UI pathway to start a donation session (F-010), and entering a Donor ID into the vitals form resulted in 404 "Donation not found" because it expected a collection visit ID. A guided wizard matches clinical blood collection reality, prevents ID mismatch errors, and lets returning donors check in without re-registration. |
| 2026-11-03 | SAD API design (BBMS-F-030) | Added `GET /api/inventory/summary` (inventory module, `routes → service → repository`), allowed for LAB_TECH, MANAGER and ADMIN; HOSPITAL and DONOR get 403. It returns `{ generatedAt, totals: { units, volumeMl, nextExpiry }, stock: [{ bloodGroup, component, units, volumeMl, nextExpiry }] }`. The existing `GET /api/inventory` unit list is unchanged. *Pending team confirmation.* | The SAD has no inventory endpoint. SAD §4.5 says manager screens show inventory and hospital users see request status, so hospitals are left out; lab techs are included because they release units from quarantine. The database does the counting (`GROUP BY`) to keep the query fast (NF-001). |
| 2026-11-03 | SRS §4.4 (AC-BBMS-F-030) | "Real-time" is done by **polling**: the dashboard re-requests the summary and unit list every **3 seconds** (the next request starts only after the previous one finishes, and polling stops when the tab is closed). There is no server push (WebSockets / SSE). *Pending team confirmation.* | Polling is simple, testable and meets the acceptance criterion: worst case is 3 s plus request time, under the required 5 s. Server push would add a library and connection handling for no gain at our scale. |
| 2026-11-03 | SRS §4.4 (BBMS-F-030) | The dashboard shows **releasable stock only**: units that are `AVAILABLE`, not past `expires_at`, ABO/Rh verified and non-reactive on all five TTI tests (the same rule as F-022). Quarantined, reserved, issued, discarded and expired units are not counted. A unit whose `expires_at` has passed drops off at once, even before any job changes its status to `EXPIRED`. *Pending team confirmation.* | Stock that can be handed out is what a manager needs to see, and sharing the F-022 rule means the dashboard can never count an unsafe unit. Counts by other statuses can be added later. Expiry alerts (F-032), FEFO (F-033) and low-stock alerts (F-034) are separate issues and are not part of F-030. |
| 2026-11-05 | SAD API design (BBMS-F-020, F-021), SRS §4.3 | Added `GET /api/lab/queue` (`lab` module), allowed for `LAB_TECH`, `MANAGER`, and `ADMIN`. Returns `{ queue, storage }` containing newly collected blood units in quarantine awaiting ABO/Rh or TTI testing, and all blood units stored in the central blood bank facility. *Pending team confirmation.* | The SAD defined testing endpoints requiring a raw donation ID, but provided no query endpoint for lab technicians to see which newly donated units are awaiting testing or to inspect stored units from the screening workspace. |
| 2026-11-05 | SAD §3.2 (RBAC Role Architecture), UI Workflows | Target group operational role restructuring: Frontline Collector + Hospital merged into `HOSPITAL` role; Tester + Storage Manager merged into `LAB_TECH` / `MANAGER`. `HOSPITAL` role authorized for `/api/donors` and `/api/donations` endpoints to operate Collection Desk. Central lab technicians (`LAB_TECH`) and managers do not see the walk-in Collection Desk. *Pending team confirmation.* | Prevents operational mix-up between chair-side walk-in donor collection and clean laboratory quarantine testing. Frontline hospital staff and phlebotomists collect blood; central facility staff test and manage inventory. |
| 2026-11-05 | SRS §4.1 (BBMS-F-001, F-002), §4.2 (BBMS-F-010) | Automated promotion of donor eligibility during chair-side draw. Walk-in registration creates a donor with baseline status `PENDING`. When chair-side vitals are entered in Step 2 of the Collection Desk Wizard, the system automatically evaluates clinical eligibility (`POST /api/donors/:id/eligibility`) using the entered haemoglobin before initiating the donation session (`POST /api/donations`). *Pending team confirmation.* | Newly registered donors have not undergone chair-side vitals at registration time. Calling `POST /api/donations` directly resulted in 422 "Donor is not eligible to donate (status PENDING)". Auto-evaluating with entered pre-vitals promotes eligible donors seamlessly while halting ineligible donors with clear clinical deferral reasons. |
| 2026-11-05 | SRS §4.3 (BBMS-F-020, F-021), STP §6 (BBMS-F-012) | Testing Queue First In First Out (FIFO) processing, 6-card pagination limit, and universal print CSS. The testing queue is sorted strictly FIFO (`collected_at ASC, id ASC`) so older units are prioritized before expiration. UI paginates to at most 6 tickets per page. Testing form cards remain collapsed below the search bar until a ticket is selected or ID entered. Universal print CSS scopes printing to only the 100mm barcode sticker across all components. *Pending team confirmation.* | Blood is perishable and must be tested in the order it was collected (FIFO). Unpaginated queues cause visual clutter, and previous print CSS caused blank printouts when printing labels from the Collection Desk Wizard. |
