| 2026-10-27 | SRS §4.2 (BBMS-F-011) | Safe ranges used to flag vitals (inclusive): systolic BP 100–140 mmHg, diastolic BP 60–90 mmHg, pulse 60–100 bpm, haemoglobin 12.5–18.0 g/dL. Readings outside the safe range are **stored and flagged** (200 with `warnings`), not rejected. Readings that are impossible are rejected with 400: ≤ 0, systolic > 300, diastolic > 200, pulse > 250, haemoglobin > 25.0, BP/pulse not whole numbers, haemoglobin with more than 1 decimal, or diastolic ≥ systolic. *Pending team confirmation.* | The issue does not give the ranges. These are team assumptions and have **not** been checked against a cited clinical standard; only the 12.5 g/dL minimum comes from our existing F-002 eligibility rule. The 400 caps also keep values inside the `SMALLINT` / `DECIMAL(4,1)` columns. |
| 2026-10-27 | SRS §4.2 (BBMS-F-011) | Post-donation haemoglobin is **not** flagged when below 12.5 g/dL (it is still flagged above 18.0). All other post-donation ranges are the same as pre-donation. *Pending team confirmation.* | A drop in haemoglobin straight after donating is expected, so flagging it would warn on almost every donor. |
| 2026-10-27 | SAD API design (BBMS-F-011) | Vitals are recorded with `PUT /api/donations/:id/vitals/pre` and `PUT /api/donations/:id/vitals/post` (LAB_TECH only, same as F-010). All four readings are required per phase; sending a phase again overwrites it. Temperature is not part of F-011 and is not captured. *Pending team confirmation.* | Pre- and post-donation readings are taken at different times, so each phase is saved on its own. Overwriting lets staff correct typing mistakes. |
| 2026-10-27 | STP §6, §10 (BBMS-F-012) | No physical label printer or barcode scanner. Labels are printed with the browser's print dialog (`Print Label`); print CSS hides the rest of the page and prints the label 100 mm wide at the top-left of the page, with its height following the content (about 56 mm). No `@page` size is set, so any paper size and orientation works. Scanning is simulated by typing the unit ID into the lookup box and pressing Enter; a USB keyboard-style scanner would do the same, but this has **not** been tried with real hardware. *Pending team confirmation.* | Required by the issue: the STP makes the printer optional. The label size is an assumption, not taken from a standard. A label-sized `@page` can be added once the team picks real label stock. |
| 2026-10-27 | SRS §4.2 (BBMS-F-012) | The barcode is **Code 128** and encodes exactly the unit ID (`blood_units.unit_code`, e.g. `U-2026-000007`). Besides the required unit ID, blood group (`PENDING` until lab testing) and collection date, the label also shows the component and expiry date. *Pending team confirmation.* | Assumption: Code 128 can encode the letters, digits and dashes in our unit IDs and is read by ordinary handheld scanners. We have **not** checked the label against any blood-bank labelling standard. Expiry and component are already on the unit and are needed to handle a bag. |
| 2026-10-27 | SAD API design (BBMS-F-012) | Units are looked up with `GET /api/donations/units/:unitId` (collection module), allowed for LAB_TECH, MANAGER and ADMIN; HOSPITAL and DONOR get 403. The code is trimmed and upper-cased first. A code that isn't shaped like a unit ID gets 400, a well-formed one that doesn't exist gets 404. The `POST /api/donations` response is unchanged. *Pending team confirmation.* | The SAD has no endpoint for unit lookup. Lab techs print labels; managers and admins may need to identify a bag. Hospitals and donors have no reason to look up bags by barcode. |
| 2026-11-02 | SRS §4.1 (BBMS-F-001, F-003), §4.2 (BBMS-F-010, F-011, F-012), SAD client architecture | Unified Blood Collection Desk Wizard replacing disconnected standalone forms. The UI guides staff through (1) Donor Check-in (new donor registration or searching existing donors by Donor ID/Phone), (2) Donation Session initialization and vitals capture in one atomic step (calling `POST /api/donations` and `PUT /api/donations/:id/vitals/pre`), and (3) immediate barcode unit label generation with post-draw recovery observation. Standalone tabs for Vitals and Labels remain available for direct lookup/reprints. | The SRS/SAD specified individual endpoints and features in isolation, which led to a disconnected UI: newly registered donors (`D-XXXXXX`) had no UI pathway to start a donation session (F-010), and entering a Donor ID into the vitals form resulted in 404 "Donation not found" because it expected a collection visit ID. A guided wizard matches clinical blood collection reality, prevents ID mismatch errors, and lets returning donors check in without re-registration. |
| 2026-11-03 | SAD API design (BBMS-F-030) | Added `GET /api/inventory/summary` (inventory module, `routes → service → repository`), allowed for LAB_TECH, MANAGER and ADMIN; HOSPITAL and DONOR get 403. It returns `{ generatedAt, totals: { units, volumeMl, nextExpiry }, stock: [{ bloodGroup, component, units, volumeMl, nextExpiry }] }`. The existing `GET /api/inventory` unit list is unchanged. *Pending team confirmation.* | The SAD has no inventory endpoint. SAD §4.5 says manager screens show inventory and hospital users see request status, so hospitals are left out; lab techs are included because they release units from quarantine. The database does the counting (`GROUP BY`) to keep the query fast (NF-001). |
| 2026-11-03 | SRS §4.4 (AC-BBMS-F-030) | "Real-time" is done by **polling**: the dashboard re-requests the summary and unit list every **3 seconds** (the next request starts only after the previous one finishes, and polling stops when the tab is closed). There is no server push (WebSockets / SSE). *Pending team confirmation.* | Polling is simple, testable and meets the acceptance criterion: worst case is 3 s plus request time, under the required 5 s. Server push would add a library and connection handling for no gain at our scale. |
| 2026-11-03 | SRS §4.4 (BBMS-F-030) | The dashboard shows **releasable stock only**: units that are `AVAILABLE`, not past `expires_at`, ABO/Rh verified and non-reactive on all five TTI tests (the same rule as F-022). Quarantined, reserved, issued, discarded and expired units are not counted. A unit whose `expires_at` has passed drops off at once, even before any job changes its status to `EXPIRED`. *Pending team confirmation.* | Stock that can be handed out is what a manager needs to see, and sharing the F-022 rule means the dashboard can never count an unsafe unit. Counts by other statuses can be added later. Expiry alerts (F-032), FEFO (F-033) and low-stock alerts (F-034) are separate issues and are not part of F-030. |
| 2026-11-05 | SAD API design (BBMS-F-020, F-021), SRS §4.3 | Added `GET /api/lab/queue` (`lab` module), allowed for `LAB_TECH`, `MANAGER`, and `ADMIN`. Returns `{ queue, storage }` containing newly collected blood units in quarantine awaiting ABO/Rh or TTI testing, and all blood units stored in the central blood bank facility. *Pending team confirmation.* | The SAD defined testing endpoints requiring a raw donation ID, but provided no query endpoint for lab technicians to see which newly donated units are awaiting testing or to inspect stored units from the screening workspace. |
| 2026-11-05 | SAD §3.2 (RBAC Role Architecture), SRS §4.2, STP §6 | Enforce role permissions strictly aligned with SRS/SAD/STP: `LAB_TECH` is the technician/phlebotomist authorized for collection (`POST /api/donations`), vitals (`PUT vitals`), and lab screening. `HOSPITAL` and `DONOR` are strictly restricted (403). In the UI, dedicated accounts separate the personas: `collector@bbms.test` (`Blood Collector`, `LAB_TECH`) operates the Collection Desk and Blood Label Tool, while `labtech@bbms.test` / `labtech2@bbms.test` (`Labtech 1` / `Labtech 2`, `LAB_TECH`) operate the Lab Screening testing queue with Collection Desk hidden. *Pending team confirmation.* | Strict conformance to the acceptance tests and RBAC specifications in the STP test harness. Avoids 403 authorization failures on collection and vitals endpoints while preserving clear separation of UI workspaces without tab clutter. |
| 2026-11-05 | SRS §4.1 (BBMS-F-001, F-002), §4.2 (BBMS-F-010) | Automated promotion of donor eligibility during chair-side draw. Walk-in registration creates a donor with baseline status `PENDING`. Calling `POST /api/donations` directly resulted in 422 "Donor is not eligible to donate (status PENDING)". Auto-evaluating with entered pre-vitals promotes eligible donors seamlessly while halting ineligible donors with clear clinical deferral reasons. |
| 2026-11-05 | SRS §4.3 (BBMS-F-020, F-021), STP §6 (BBMS-F-012) | Testing Queue First In First Out (FIFO) processing, 6-card pagination limit, and universal print CSS. The testing queue is sorted strictly FIFO (`collected_at ASC, id ASC`) so older units are prioritized before expiration. UI paginates to at most 6 tickets per page. Testing form cards remain collapsed below the search bar until a ticket is selected or ID entered. Universal print CSS scopes printing to only the 100mm barcode sticker across all components. *Pending team confirmation.* | Blood is perishable and must be tested in the order it was collected (FIFO). Unpaginated queues cause visual clutter, and previous print CSS caused blank printouts when printing labels from the Collection Desk Wizard. |
| 2026-11-06 | SRS §4.2 (BBMS-F-013) | Offline camp recording is a **simplified browser queue**, not a full offline app. The Collection Desk has an "Outreach camp" mode. Every camp record is saved in the browser's `localStorage` first (one queue per logged-in user, kept across logout and page reloads), then sent to the server: straight away if online, automatically when the `online` event fires, or with **Sync now**. Records are sent in chunks of 50, one after another; a network error, expired login (401) or server error stops the sync and leaves the rest queued. Automatic syncs send only pending records; **Sync now** also re-sends records the server rejected, which stay listed with the server's reason until they sync or are removed. Only **existing donors** can be recorded (Donor ID typed in, because donor search needs the server); consent and new-donor registration are not captured offline. Each record gets a browser-made UUID; its first 8 characters are a temporary reference written on the bag, and the **barcode label is printed after sync**, when the server has given the unit its ID. There is **no service worker**: if the page is reloaded or the tab is closed while offline, the app will not load until the connection returns (the queue itself is kept). Staff must open the app and log in before going offline and keep the tab open. *Pending team confirmation.* | The issue allows a simplified approach. `localStorage` is synchronous and easy to test; a camp produces far fewer records than its size limit. Saving first and syncing later means a record is never lost because the connection drops halfway. Unit IDs come from the database, so a final label can only be printed after sync. A service worker would add caching and update handling that we cannot test properly in this sprint. |
| 2026-11-06 | SAD API design (BBMS-F-013) | Added `POST /api/donations/sync` (collection module, LAB_TECH only like F-010; others get 403). Body `{ records: [...] }` with 1 to 50 records, otherwise 400 for the whole request. It answers 200 with one result per record: **201** created, **200** already synced (the same `clientRef` was saved before; the existing donation and unit are returned and nothing new is created), **400** invalid input, **404** unknown donor, **422** consent missing, donor not eligible or unit already expired. Each record is saved in its own transaction (donation, unit, audit row). The original camp `collected_at` is kept; it may be at most **5 minutes** in the future (clock skew), and the unit's expiry is counted from it. Eligibility is checked again at sync with the camp haemoglobin, the donor's age and a 90-day gap measured from the camp collection time (any earlier donation that was not aborted counts). A PENDING donor who passes is set to ELIGIBLE, like the desk does; a rejected record does **not** change the donor's status. Camp donations are saved as `COMPLETED`, because the draw is already over when they are recorded. *Pending team confirmation.* | The SAD has no sync endpoint. Per-record results let one bad record be fixed without blocking the rest of the camp. A replayed record must return the original so retries after a timeout never duplicate a donation. The 5-minute allowance and the 90-day rule from the camp time are team assumptions. |
| 2026-11-06 | SAD data model (`donations`) | Added `donations.client_ref CHAR(36) NULL UNIQUE`. It holds the browser-made UUID of a synced camp record and is `NULL` for desk sessions and seed data. *Pending team confirmation.* | The unique key is what guarantees "no duplication" in F-013: even two syncs of the same record at the same moment can only save it once. |
| 2026-11-06 | SRS §4.1 (BBMS-F-001, F-003, SR-002), SAD client architecture | Official physical CR80 Donor Identity Card (print isolation and 2x retina PNG export) and Donor Self-Service Portal (`GET /api/donors/portal/me`, `POST /api/auth/change-password`). Walk-in registration atomically provisions a web portal login account with default password syntax `DDMMYYYY` (from Date of Birth). Government ID proof is masked to only the last 4 characters (`****XXXX`) and no passwords or pending test states are displayed on the card itself. *Pending team confirmation.* | Gives walk-in donors an official physical identification card immediately at collection desk check-in and empowers donors to track their eligibility and records remotely. Password masking and removing pending test labels preserves privacy on physical cards. |
| 2026-11-06 | SRS §4.4 (BBMS-F-031) | A whole-blood unit can be separated into PRBC, FFP, Platelets and Cryo (any set, each once) from the Blood Label Tool. Each component is a new `blood_units` row with its own unit ID (same generator as F-012) and a `parent_unit_id` link to the whole-blood bag; it copies the bag's `donation_id`, blood group, status and **collection time**. The bag is set to a new status `SEPARATED`, so it can never be released, issued or counted again, and it can only be separated once. Separation is allowed while the bag is in **QUARANTINE** (and when AVAILABLE), not when it is reserved, issued, discarded, expired or past its expiry time. **Component expiry is counted from the bag's collection time, not from the separation time**: PRBC 42 days, FFP 1 year, Platelets 5 days, Cryo 1 year; a component that would already be expired is refused (e.g. platelets from a bag more than 5 days old). Default volumes for a 450 mL bag: PRBC 280 mL, FFP 200 mL, Platelets 50 mL, Cryo 15 mL (can be overridden per request); the total is not checked against the bag volume. Apheresis units are recorded as Platelets (F-010), so they are not whole blood and cannot be separated. *Pending team confirmation.* | The issue needs each component traceable to its donation. Lab results belong to the donation, so components made in quarantine are released or discarded with it (F-022/F-023) without retesting. A separate status keeps the bag's history without counting it as waste or stock. Counting expiry from collection means separating a bag can never extend its blood's life. Shelf lives, volumes and the missing volume check are team assumptions not checked against a cited standard (PRBC volume includes additive solution, and Cryo is made from plasma). |
| 2026-11-06 | SAD API design (BBMS-F-031) | Added `POST /api/inventory/units/:unitCode/separate` with `{ components: [...], volumes?: { PRBC: 250 } }` -> 201 `{ parent, children }`, and `GET /api/inventory/units/:unitCode/lineage` -> 200 `{ unit, parent, children, siblings, donation }` (inventory module). Both are for LAB_TECH, MANAGER and ADMIN; HOSPITAL and DONOR get 403. Separation answers 400 for a malformed unit ID or component list, 404 for an unknown unit, 409 if it was already separated or is no longer in the bank, and 422 if it is not whole blood or a component would already be expired. It runs in one transaction with the bag row locked, so two separations of the same bag can never both succeed, and it writes `UNIT_SEPARATED` / `COMPONENT_CREATED` audit rows. `GET /api/donations/units/:unitId` (F-012) now also returns `parentUnitCode`, and a component's label shows "From <parent unit ID>". *Pending team confirmation.* | The SAD has no component endpoints. The roles match the label lookup and inventory summary: blood-bank staff only. |

| 2026-11-12 | SRS §4.5 (BBMS-F-041), SAD API design (`request` module) | Cross-match recording (`POST /api/blood-requests/:idOrCode/crossmatch`), issuance readiness validation (`GET /api/blood-requests/:idOrCode/crossmatch/:unitCode/check`), and cross-match history (`GET /api/blood-requests/:idOrCode/crossmatches`). | 2026-11-12 | SRS §5.1.2 (BBMS-SR-003), SAD security architecture | Implemented AES-256-GCM encryption at rest for sensitive personal and medical data (`medical_history`, `address`, `deferral_reason`, `follow_up_reason`) in MySQL (`donors` table) via `server/src/utils/encryption.js`. Encrypted fields are stored in standard authenticated ciphertext format (`enc:v1:<iv>:<tag>:<ciphertext>`) on disk and automatically decrypted upon retrieval for authorized API endpoints and client portals. Legacy unencrypted rows are handled transparently without error. 256-bit key is loaded from `ENCRYPTION_KEY` / `DATA_ENCRYPTION_KEY` or derived via SHA-256 from system secrets. *Pending team confirmation.* | Satisfies BBMS-SR-003 and TC-Sec-03 security requirement to safeguard personally identifiable information and medical history at rest against unauthorized database dumps, disk theft, and host-level access while maintaining seamless backward compatibility with existing services. |
| 2026-11-12 | SRS §4.4 (BBMS-F-032), SAD API design (`inventory` module) | Near-expiry alerts endpoint (`GET /api/inventory/alerts/expiry`, alias `GET /api/inventory/expiry-alerts`) with configurable threshold query parameter (`thresholdDays` or `days`, defaulting to 3 days, bounded between 1 and 60 days). | 2026-11-12 | SRS §4.4 (BBMS-F-033), SAD API design (`inventory` / `request` module) | FEFO allocation suggestion endpoints (`GET /api/inventory/fefo` and `GET /api/blood-requests/:idOrCode/fefo-suggestions`).
